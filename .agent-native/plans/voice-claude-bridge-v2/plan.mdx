<Callout id="recap-scope" tone="info">

**Scope:** the three commits on `feat/voice-claude-bridge` above `d852408` — v2 design spec, implementation plan, and the box-side implementation. The Happy **app** side (`RealtimeVoiceSession.tsx`, `voiceHooks.ts`, `types.ts`) is deliberately **not** included; it needs an APK rebuild and the bridge degrades gracefully until it ships.

</Callout>

The v1 bridge pipes voice to Claude via `happy-agent`, but targets the **newest-active** session — with multiple sessions it sprays across them per utterance and can hit the control session. v1 mitigates by pinning one `VOICE_SESSION_ID`. The real fix: the **phone knows focus, the box does not**. v2 gets the focused-session id from the phone over the existing LiveKit data channel so voice routes to the session the user is looking at, plus a **completion ping** when a background session finishes.

The decision was **Route B** — the Happy app `publishData`s two structured message types (`focused_session`, `session_complete`) the Python agent consumes. Rejected: parsing existing human-readable focus strings (brittle), polling `happy-agent status` (races, latency). Voice-approve permissions stay out of scope — `happy-agent` has no `allow`/`deny` CLI.

### Session-targeting contract

The core behavioural change is a new resolution priority. Voice now routes to `override → focused → newest-active` instead of v1's `override → newest-active`. The `focused` id comes from the phone's `focused_session` data-channel message and lives in a shared `VoiceState` object on the agent's event loop.

<Column id="resolve-before-col" label="Before (v1)">

```python
def resolve_session_id(run=_default_run, override=None):
    """the override if given, else the most-recently-active session."""
    if override:
        return override
    sessions = json.loads(run(["list", "--active", "--json"]))
    ...
    return sessions[0]["id"]
```

</Column>
<Column id="resolve-after-col" label="After (v2)">

```python
def resolve_session_id(run=_default_run, override=None, focused=None):
    """override → focused → most-recently-active session."""
    if override:
        return override
    if focused:
        return focused
    sessions = json.loads(run(["list", "--active", "--json"]))
    ...
    return sessions[0]["id"]
```

</Column>
</Columns>

A completion ping fires only for a **background** session (one whose id ≠ the focused id) to avoid double-speak — if the user is looking at it, the v1 reply path already speaks the turn result. Failures are graceful: no focus received → newest-active fallback; malformed data message → logged + ignored; old APK that never sends the new types → v1 behaviour unchanged.

### Compatibility notes

- **`resolve_session_id` signature widened** with a `focused=None` kwarg — backwards compatible; v1 callers omitting it get the newest-active path. The two `happy_llm` tests that called `resolve_session` via `lambda override=None` were widened to `lambda override=None, focused=None` to accept the new kwarg.
- **`HappyBridgeLLM.__init__` gains `voice_state=None`** — optional, so existing constructions without it still work (focused resolves to `None` → newest-active).
- **`active_sessions_with_summary` return shape** carries `activeAt` and is sorted newest-first — single `happy-agent list` call per seed/refresh instead of two.

### Verification

39/39 pytest green (v1's 17 + 22 v2 new). The voice-agent systemd service restarted clean with the v2 code — worker registered, whisper + kokoro loaded, no traceback. The pre-existing `torio`/FFmpeg `libavutil.so` warnings are unrelated environmental noise the agent has always run under.

### Not in this recap (intentional)

The Happy app side — `RealtimeVoiceSession.tsx`/`.web.tsx` (`sendStructuredMessage`), `voiceHooks.ts` (`onSessionFocus`/`onReady` emit), `types.ts` (`VoiceSession` interface) — is **not** implemented here. It needs an APK rebuild and is tracked as Phase 6 of the plan. Until it ships, the box degrades to v1 newest-active behaviour with no focus or completion-ping messages arriving. Deferred backlog items #6 (streaming + acknowledgment) and #7 (turn detection / endpointing) are also out of scope.
